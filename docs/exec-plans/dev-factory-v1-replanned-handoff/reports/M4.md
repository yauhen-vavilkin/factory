## Fixes (each reproduced, regression-checked, verified)

1. **Scripted smoke residue** (`scripts/factory`): every `smoke --pi --scripted` run leaked one Pi-written fixture plus two verification clones into `.factory/data/sandboxes/` (~29 MB/run; 51 dirs / ~364 MB and 8 leaked `factory-pi-smoke-*` networks accumulated before M4). Root cause: no cleanup code, and the fixture contains uid-10001-owned git objects the host user cannot remove. Fix: EXIT-trap cleanup of the run's own workspaces and network, with a root-helper `alpine` reclaim step for container-owned files, plus a post-cleanup assertion (`workspace_cleanup=PASS`) that makes every future smoke run the regression test. Verified: run before (residue 51→54 dirs) and after (0 residue, 0 leaked networks, 63 s, exit 0). Historical residue and leaked networks were cleared once and documented.
2. **Gateway artifact-limit regression** (`factory-gateway/test_gateway.py`, new; `factory-gateway/server.py`): hermetic loopback test suite pinning the corrected 64 MiB boundary — 23 MiB required-artifact class passes (low-002 regression), over-cap artifacts are rejected with 502, the model route stays disabled on the dependency gateway, missing/revoked run tokens return 401 before any upstream contact, traversal is rejected, and unapproved upstream bases fail at startup. `server.py` gained only an env-overridable evidence directory (production default unchanged) to keep the suite hermetic. Wired as `./scripts/factory validate --gateway` (10 tests, exit 0).
3. **Hard-killed launcher permanently blocks restart** (`scripts/factory`): the mkdir-based `start.lock` cannot be released after SIGKILL. Demonstrated with the b4b0236 launcher: kill -9 during start → retry fails forever with "another Factory start is in progress". Fix: kernel-released `flock` on a lock file, with one-time migration of an empty legacy lock directory. Verified: stale directory migrated, start proceeds (43 s to ready); concurrent-start protection preserved.
4. **Silent execution-history loss across the M3 compose storage change** (`scripts/factory` + data repair): pre-M3 PostgreSQL lived in the named volume `factory_factory-pgdata`; the M3 compose switched to the `.factory/data/postgres` bind mount, and any `compose up` on the changed service silently starts a fresh cluster, hiding the old rows (observed: 3 executions, 8 artifacts invisible; `show`/`export` 404). Repair: legacy volume imported with a data-only dump (3 executions / 8 artifacts / 34 audit events; `flyway_schema_history` and the live `flow_registry` untouched), dump archived at `.factory/data/legacy-pgdata-import-20260911.sql`, legacy volume retained as archive; `show`/`export` of the restored execution verified. Fix: fail-closed guard in `infra up` and `start --mode pi` that refuses to run while the legacy volume exists without the `.factory/data/postgres.legacy-imported` marker; negative-tested both ways.

Items 1, 3, 4 are the three issue-sized fixes; item 2 is the required regression for the M3-corrected limit. No DEFERRED.md work was implemented.
