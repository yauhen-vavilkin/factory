# Prompt: Developer Flow cleanup (code and legacy configuration)

Intended runner: Claude Code session at the repository root, Claude Opus 5.5, effort xhigh, Docker running
(Testcontainers and `mvn verify` need it). Expected duration: several hours. Work autonomously; do not stop
to ask questions. When something is unclear, choose the smaller change, write the reason into the status
section of the audit file (see "Reporting") and go on.

## Your role

You are a senior Java engineer cleaning up a Spring Boot codebase that was mostly generated by AI tools.
The product works and its behaviour is accepted. Your job is to make the code smaller, plainer and more
honest without changing what the operator sees or can configure, except for the legacy configuration
layers listed below, which are removed on purpose. You are not here to redesign anything: no new packages,
no new layers, no new abstractions beyond the few named in this prompt, no renaming for taste, no new
configuration keys, no new Checkstyle suppressions. "Minimal" never means dropping input validation at
trust boundaries, error handling, security or accessibility.

1. `AGENTS.md` (whole file). Its "Product postulates", "Developer Flow invariants", "Code style" and
   "Testing conventions" sections are binding.
2. `docs/superpowers/specs/2026-10-30-dev-flow-code-audit.md` (whole file). It is the evidence base for

## Rules that apply to every change

- Behaviour is unchanged for the operator: same pages, same words, same artifacts, same audit events,
  same JSON field names in artifacts, audit details and `task_attempt` columns, same error texts. The only
  intended visible change is that the removed legacy configuration keys stop being read (a stale `.env`
  then fails or warns loudly; it must never silently change a destination or a credential).
- The Developer Flow invariants from `AGENTS.md`: secrets never reach the database, artifacts, logs, argv
  or pages; hidden reasoning never reaches a transcript or page. The `HIDDEN_*_SENTINEL` checks in
  `UiRenderSmokeTest` and `ClaudeCodeCodingRuntimeTest` and
  `DeveloperExecutionViewTest#rendersConservativePiLifecycleLabelsWithoutMessageOrReasoningContent` stay
  and keep passing.
- Tests: never weaken an assertion to make a test pass. A test changes only when the behaviour it asserts
  was removed on purpose by this prompt (then delete or adapt it and say so in the commit message) or when
  it constructs a type whose test-only constructor you removed (then use a test fixture). Test counts per
  module are recorded before and after; every decrease is explained by a deleted feature-less test.
- Checkstyle: `mvn -B -ntp validate` is clean after every phase. Delete a suppression as soon as its
  method is under the limit. Never add one.
- Code style as in `AGENTS.md`: methods of at most 25 lines, at most 7 parameters, one job per class,
  classes under about 300 lines, `@RequiredArgsConstructor` for beans, `var` where the type is visible,
  guard clauses, records for data, enums for kinds, `Optional` for lookups that can miss, `Map<String,
  Object>` only at open JSON boundaries. Comments say why, never what. Plain English, B2 level, in code
  comments, UI text and commit messages.
- One commit per phase (two if a phase has an independent half). Commit messages follow the style in
  `git log`: a short imperative subject, then a body that names what was removed and the evidence that it
  was dead or duplicated. Never push. Never rebase or touch `main`.
- Measure before you start: `mvn -B -ntp clean verify`, then record per module the number of tests run
  and skipped from `*/target/surefire-reports/TEST-*.xml` and the wall-clock time. Repeat at the end.

## Self-review protocol

After each phase and before its commit, review your own diff against this checklist. If your environment
offers a review sub-agent, give it the diff and the checklist, not your conclusions, and act on what it
finds.

- Behaviour: every page, artifact, audit event, error text and JSON key the operator could see is the
  same, except the removed legacy configuration. For config removals, the failure mode of a stale `.env`
  is loud.
- Nothing new: no new package, no new abstraction beyond `TaskGuard`, `Stop`, `Git`, `DecisionGates`,
  `TokenUsage`, `DevFactoryHooks`, the parameter records and the test fixtures; no new config key; no new
  suppression; no `@Data`, `@SneakyThrows`, setters on artifact or audit entities.
- Redaction paths intact: every string from the coding CLI still goes through `CodingRuntime.redact`;
  nothing in `ClaudeCodeProtocol`'s handling of thinking blocks changed.
- Tests: counts explained, no weakened assertion, fixtures replace removed constructors, round-trip tests
  exist for every JSON-bearing type you touched.
- Checkstyle clean, `mvn -B -ntp verify` green, Docker-gated tests still skipped cleanly without
  `FACTORY_DOCKER_TEST`.
- The commit message says what was removed and why it was dead or duplicated, in plain English.

## When things go wrong

- A claim in the audit does not hold: skip the item, record it, continue.
- `mvn verify` fails for an environment reason (Docker down, port in use): fix the environment if you can;
  otherwise stop and report. Never mark a phase done with a red build.
- A test fails after a change and you cannot tell whether the test or the change is wrong: read the test's
  intent in `AGENTS.md` terms (required, observable behaviour), decide, and write the reasoning into the
  commit message. When still unsure, revert that single change and record it as skipped.
