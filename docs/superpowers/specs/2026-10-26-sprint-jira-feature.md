# Мои задачи из Jira → PR: как работает фича

Статус: утверждён оператором 2026-10-26, вопросы дизайна закрыты. Дальше перенос дизайна в
HTML-макет в репозитории, потом план и реализация в этой же сессии.

Фабрика личная: помощник одного разработчика, запускается у него локально командой
`docker compose up -d`. Разработчик назначает задачу на себя в Jira и видит её на странице
Developer Flow. Он выбирает одну или несколько задач и жмёт Run, задачи выполняются по очереди,
по одной. Если нужной задачи нет среди назначенных, он вводит её ключ и добавляет на выполнение.
Каждая задача заканчивается PR от его имени, его токеном, или понятной причиной, почему нет.
Запуск по ключу, как раньше, остаётся; автоподбор, выбор нескольких задач и очередь его
дополняют, но не ломают.

## 1. Сценарий по шагам

| Ситуация | Что человек делает | Что видит | Действий |
| --- | --- | --- | --- |
| Первая настройка | `cp .env.pilot.example .env`; вписать имя как в Jira и токен GitHub; поднять прокси CodeMie; `docker compose up -d`; открыть страницу флоу; Scan Jira | Свои назначенные задачи в Available | 6, плюс создание токена GitHub |
| Обычный день | Назначить задачу на себя в Jira; открыть страницу; Scan Jira; отметить N задач; Run | Задачи переходят в Triggered: очередь, стадия, стоимость, потом ссылка на PR | N+3 |
| Задача не из моего списка | Вставить ключ или ссылку; «Add to run» | Задача сразу в Triggered, в общей очереди | 2 |
| Задача не получилась | В строке Triggered видны причина и потраченное; Retry в строке | Новая попытка встаёт в очередь | 1 |
| Новый спринт | Ничего сверх обычного дня | Новые назначенные задачи появляются после Scan Jira | 0 |
| Сменить имя или токен | Правка `.env`; `docker compose up -d` | Список по новому имени | 2 |

Рантайм кодинга: Claude Code с моделью sonnet-5-5; CodeMie это провайдер инференса (прокси на
порту 4001), его разработчик поднимает сам.

## 2. Правила Jira-части

- Источник: задачи Jira, назначенные на меня. Спринта и борды нет.
- Кто такой «я»: одна переменная с полным именем как в Jira или accountId (Jira принимает обе
  формы). Ключ Jira не нужен. Опечатка в имени даёт пустой список без ошибки, поэтому на экране
  видно, по какому имени идёт поиск, и есть ссылка «открыть этот поиск в Jira».
- Статусы: скан берёт все мои незакрытые задачи (`statusCategory != Done`). Над списком
  Available чипы статусов с числом задач, клик скрывает или показывает строки; по умолчанию
  включены Open и In Progress. Настройки статусов в конфигурации нет.
- Скан: только по кнопке Scan Jira. Автоскана по расписанию в этой итерации нет.
- Подходит: проект задачи сопоставлен ровно с одним репозиторием в
  `config/developer-repositories.yaml`. Не подходит: проект не настроен, репозиторий для него
  не задан; на экране так и пишем. Связи задачи в Jira на «подходит» не влияют, решает человек
  кликом; агент получает связи как контекст.
- Задача по ключу или ссылке: любой статус, любой исполнитель (например, тесты и эвалы по уже
  сделанным задачам). Идёт в Triggered как остальные: общая очередь, стоимость, PR, Retry.
  Проект не настроен: отказ сразу, с причиной.
- Запущенная задача держится независимо от фильтра: смена статуса или исполнителя в Jira её
  не отменяет.
- Запуск всегда кликом, дальше задача сама идёт до PR без вопросов. Режима Automatic нет.
- Очередь: выполняется одна задача за раз. Run, Add to run и Retry ставят попытку в очередь;
  если ничего не выполняется, она стартует сразу, иначе ждёт (Queued). Порядок очереди: по
  времени клика (сейчас в коде по дате создания задачи в Jira, меняется одной строкой запроса).
- Провал задачи (Could not complete, в том числе отказ провайдера) освобождает слот: очередь
  сама идёт к следующей задаче. Держит очередь только Needs inspection (фабрика не смогла
  доказать, что запуск остановился) и перепроверяет её раз в минуту. Над Triggered тогда строка
  «Queue is waiting» и кнопка «Mark as stopped…» с подтверждением: задача становится
  Could not complete, очередь идёт дальше. Слово Release не используем: у него свой смысл во флоу.
- При Run и Add to run фабрика проверяет, может ли токен GitHub пушить в репозиторий
  доставки. Если нет, задача не ставится в очередь, причина видна сразу после клика.
- PR создаётся от имени разработчика его токеном GitHub. Куда идёт PR, задаёт только
  репозиторий доставки: folio-org по умолчанию из каталога, форк двумя переменными репозитория
  (источник и доставка), как в шаблоне сейчас.
  Флага `*_DELIVERY_AUTHORIZED` нет: он срабатывал только на шаге PR, после оплаченной работы,
  и дублировал выбор репозитория доставки.
- Настройка для первого запуска: две переменные, `FACTORY_PILOT_ASSIGNEE` и
  `FACTORY_CONNECTORS_GITHUB_TOKEN`. Jira (`folio-org.atlassian.net`), рантайм и
  переключатели получают значения по умолчанию; скан работает, когда задано имя. Остальные
  переменные шаблона необязательны (например, форк).

Проверено анонимными GET к Jira FOLIO 2026-10-26: статуса `To Do` нет (Open, In Refinement,
Draft, In Progress…); задачу назначают, когда берут в работу; поиск по `assignee` без ключа
работает и по имени, и по accountId; у 50 из 51 задачи в Open/In Progress есть связи.

## 3. Экран

Итоговый макет: [`../mockups/my-tasks-v3/`](../mockups/my-tasks-v3/flow.html), статичный
рендер холста Claude Design (холст временный, удаляется после реализации). Отличия от
прежней базы [`../mockups/flow-sprint-work-v2.html`](../mockups/flow-sprint-work-v2.html):

- Карточка спринта становится карточкой «мои задачи»: имя, по которому ищем, статусы, время
  последнего скана, Scan Jira, «Open this search in Jira». Имени и дат спринта нет, строки
  «auto-scan every 5 min» нет.
- Вкладки страницы флоу: «My tasks | Definition».
- У Developer Flow нет JSON-запуска («Trigger flow»): путь запуска один, галочки или ключ.
  У других флоу кнопка остаётся.
- Уходят блок Admission и «Switch to automatic…».
- Новое поле под списком Available: ключ или ссылка на задачу и кнопка «Add to run».
- Над Available чипы статусов Jira; в строке задачи колонка «In Jira» со статусом.
- Not eligible бывает по двум причинам: проект не настроен или проект указан у нескольких
  репозиториев.
- В Triggered у задач, добавленных по ключу, метка «added by key»; метки «Outside current
  filter» нет.
- В Triggered нет состояния Withdrawn.
- Retry: кнопка прямо в строке Triggered (1 клик) и на сводке задачи.

Страницы (дизайн на холсте Claude Design, решение 2026-10-26). Адреса: My tasks на
`/flows/dev-factory`, вкладка Definition на `/flows/dev-factory?view=definition`, сводка
задачи на `/tasks/{id}`; старый `/tasks` ведёт на страницу флоу, пункта Tasks в меню нет.

- Сводка задачи (нынешний `pilot-task.html`): результат, Retry, ссылка на последний запуск,
  попытки, общая стоимость и токены, Technical details.
- Живой вид одной попытки остаётся на существующей странице запуска (`execution.html`),
  перерисованной: Now, стадии, Activity (runtime-лог), Runtime and usage, Technical details.
  Строка Working в Triggered ведёт сразу на запуск. Живое обновление уже есть: опрос и
  перезагрузка страницы, таймеры тикают в браузере.
- PR feedback (комментарии ревью, раунды доработки) остаётся на странице запуска, как сейчас;
  на сводке PR ready ссылка «Work on PR feedback».
- Принцип: на экранах только данные, которые код уже даёт или даёт малой правкой.

## 4. Действия пользователя и зачем они нужны

| Действие | Зачем |
| --- | --- |
| `cp .env.pilot.example .env` | В `.env` лежит токен, он не попадает в git; шаблон показывает, что вписать |
| Вписать имя в `.env` | Фабрика знает, чьи задачи показывать |
| Вписать токен GitHub | PR создаётся от моего имени |
| Поднять прокси CodeMie | Через него идёт инференс модели |
| `docker compose up -d` | Единственная команда запуска |
| Открыть страницу флоу | Единственное место: мои задачи, запуск, очередь, PR |
| Назначить задачу на себя в Jira | Это и есть выбор «задача моя»; команда видит, чья задача |
| Scan Jira | Фабрика узнаёт о новых и изменившихся задачах только по кнопке; автоскана нет |
| Отметить задачи галочками | Часть своих задач делаю руками, фабрика берёт только отмеченные |
| Run / Add to run | Явное согласие потратить деньги и получить PR |
| Retry | Повтор стоит денег, поэтому только явно; причина и потраченное видны в той же строке |
| Mark as stopped… | Редкий случай: фабрика не может сама доказать, что запуск закончился, и держит очередь; подтверждение, потому что при живом запуске пошли бы два одновременно |

## 5. Что не делаем в этой итерации

- Спринт и борду как источник задач.
- Метки в Jira как источник: фабрики разных разработчиков конфликтовали бы за задачи.
- Режим Automatic, в котором фабрика сама запускает задачи без клика.
- Правило «есть связь в Jira, значит не подходит».
- Флаг разрешения публикации на каждый репозиторий.
- Особую обработку эпиков и подзадач: в командах они пока не используются.
- Оценку, осилит ли фабрика задачу.
- Пагинацию списка Available.
- Автоскан по расписанию: скан только по кнопке.

## Потом

- Автоскан по расписанию (cron).
- Параллельное выполнение нескольких задач (сейчас диспетчер держит один активный слот).
- Пагинация Available, если список станет длинным.
- Оценка сложности задачи перед запуском.
- Ключ Jira (email и токен, запрос `currentUser()`) для закрытой Jira.
