# Модели в одном файле и форма запуска на My tasks

Статус: решения согласованы с пользователем 2026-11-01 и 2026-11-03, макеты лежат на холсте
«Factory My tasks UI» (доски My tasks, Not configured dialog, Model config). Дальше реализация
в `m1-sprint-pilot`.

Factory запускает у себя и настраивает один и тот же человек. Он описывает в конфиге, какие
модели у него есть, и при запуске выбирает модель и effort. Отдельной роли «оператора» нет.

## 1. Конфиг моделей

Один файл `config/developer-models.yaml`, ключ `factory.dev-factory.models`. Это плоский список,
одна запись на одну модель у одного провайдера, по образцу `model_list` в LiteLLM и `models` в
Continue. Та же модель у другого провайдера это ещё одна запись со своей ценой. Файл заменяет
`config/developer-run-profiles.yaml`, `config/developer-pricing.yaml` и модельные переменные
`FACTORY_CLAUDE_CODE_*` (профиль `env-default` уходит).

| Поле | Обязательно | Что это |
| --- | --- | --- |
| `id` | да | Имя в списке Model, строчные буквы, цифры, точки, дефисы |
| `api` | да | Протокол endpoint: `anthropic-messages` или один из типов Pi 0.85.1 |
| `base-url` | да | HTTP(S) без логина, query и fragment |
| `authentication` | да | `api-key` или `bearer-token` |
| `secret-env` | да | Имя переменной `.env` с секретом; сам секрет в файл не пишется |
| `model` | да | Строка модели, которую получает endpoint |
| `efforts` | да | Уровни effort модели, по порядку |
| `default-effort` | да | Один из `efforts` |
| `max-output-tokens` | нет | По умолчанию 16384 |
| `price` | нет | Цена за миллион токенов, блоком: `currency`, `as-of`, `source` (https) и `*-per-million` |

Ошибка в файле останавливает старт с сообщением, где названы запись и поле: повтор `id`,
неизвестный `api`, `default-effort` не из `efforts`, плохой URL, цена без валюты, даты или
https-источника, отрицательная цена.

В `.env` остаются секреты, выбор harness (`FACTORY_DEV_FACTORY_CODING_RUNTIME`), лимиты и
модель по умолчанию `FACTORY_DEV_FACTORY_DEFAULT_MODEL`. Если она пуста, по умолчанию берётся
первая запись файла, чей `api` понимает harness. Готовность записи на выбор по умолчанию не
влияет: неготовая модель по умолчанию видна на Check configuration с причиной.

Docker Compose передаёт в контейнер только перечисленные переменные, поэтому каждая
`secret-env` записана и в `docker-compose.yml`. Причина неготовности это говорит.

## 2. Какие модели видны в форме

Модель видна в списке Model, если её `api` понимает установленный harness, её efforts есть у
этого harness и её секрет задан. Claude Code понимает только `anthropic-messages` и effort
`low, medium, high, xhigh, max`. Остальные записи видны на Check configuration с причиной.
Если готовая модель одна, список Model скрыт.

Pi в этой работе не меняется: модель и уровень он берёт из `FACTORY_PI_*`, формы выбора у
него нет. Файл моделей Pi использует только для цены (по строке модели); свой ключ Pi
скрывает сам, как раньше.

## 3. Max turns

Поля в форме нет. `FACTORY_CLAUDE_CODE_MAX_TURNS` это предохранитель, по умолчанию 200, от 1
до 500. Раньше срабатывает таймаут кодинга 30 минут, это около 180 ходов. Сохранённое в старых
попытках число ходов не используется.

## 4. Сохранённые настройки запуска

Имена в JSON остаются прежними, чтобы старые попытки и артефакты читались: `profileId` теперь
хранит `id` записи модели. `maxTurns` больше не пишется, старое значение пропускается.
`env-default` и пустое значение означают модель по умолчанию. Записи `glm-5.3` и
`glm-5.3-flash` сохраняют свои `id`: на них ссылаются попытки, у которых открыт PR.

## 5. Цена

Цена берётся из записи модели в начале запуска и сохраняется в попытке, как раньше. Поиск идёт
по `id` записи. Если `id` нет (Pi, старые шаги), ищется запись по строке модели, и только когда
такая запись одна. Иначе цена неизвестна и стоимость помечается «may be higher».

## 6. My tasks

Как на доске My tasks:

- Карточка источника: заголовок, ⓘ с двумя предложениями, Last scan, Scan Jira. Ошибки
  (исполнитель не задан, скан упал) остаются на карточке. Второй строкой поле «Not in your
  list?» и Add to list.
- Available: сверху Model и Run, у каждой строки, которую можно запустить, переключатель
  Effort из уровней выбранной модели (радиокнопки, работают без JS). Смена модели
  перестраивает переключатели под её уровни, по умолчанию её `default-effort`.
- Строка ключа: ключ, чип репозитория или красный чип, метка added by key. Все чипы одной
  высоты. Красный чип Not configured (нет репозитория для проекта) или Several repositories
  (проект в нескольких записях) открывает окно с причиной и шагами; без JS это ссылка на
  страницу задачи.
- Triggered: чип репозитория в строке ключа вместо «→ repo».
- Retry на странице задачи: те же Model и Effort, поле инструкций, без Max turns.

Тип причины неготовности (`NO_REPOSITORY`, `SEVERAL_REPOSITORIES`) читается из сохранённого
`routing_reason` тем же классом, который этот текст пишет (`TaskRoutingReason`), как уже
читается причина готовности. Сам текст не меняется: он входит в `destinationFingerprint`.

## 7. Добавление по ключу

Задача по ключу попадает в Available с меткой added by key, а не сразу в очередь. Запуск
дальше обычный: отметить, выбрать effort, Run.

- В задаче хранится флаг `added_by_key` (миграция V17). Скан не убирает такие задачи из
  списка. Если скан находит задачу назначенной на меня, флаг снимается.
- Remove убирает задачу из списка.
- Уже запускавшуюся задачу поле не добавляет: «уже запускалась, Retry в Triggered». Задачу,
  которая уже в списке, тоже.
- Задача из проекта без репозитория добавляется с красным чипом.
- Попытка такой задачи записывается как `BY_KEY`.

Перезапуск задачи с открытым PR по ключу уходит (см. open questions).

## 8. Check configuration

- Таблица Models вместо Run profiles: все записи файла, готова или нет и почему, endpoint,
  цена, efforts. Проверки моделей вынесены в отдельный класс.
- Карточка «My tasks source»: исполнитель, Jira, запрос, ссылка на поиск, какие проекты в
  какие репозитории идут.
