## 1. Входная точка: где оператор начинает делегирование

**Статус: решено (2026-10-25) — flow-центричный вход, делегирование — способность флоу.**

Оператору предложены три варианта входа: A — Tasks-инбокс (единственная рабочая
поверхность, флоу/скоуп/спринт названы в шапке, ссылки с дашборда и страницы флоу);
B — вход на странице флоу (кнопка сканирования + выбор задач на `/flows/dev-factory`);
C — хелпер-лаунчер, запускающий задачи параллельно/последовательно.

Оператор вариант не выбрал и переформулировал проблему (дословно): «Так просто и не
ответить. Надо вот это и обсуждать… Вот как будет выглядеть task inbox? …у нас же
условно платформа может содержать несколько разных flow. Это логично и понятно. То
есть, если я, например, выберу тест флоу для выполнения спринта, я тестировщик. Я
хочу запустить работу для своего флоу. Что мне делать?»

Зафиксированные требования из ответа:

- Решение о входной точке — только после визуального рассмотрения инбокса
  («порисовать»), не в абстракции.
- Дизайн обязан отвечать на ментальную модель «платформа = много флоу»: путь
  тестировщика со своим флоу должен быть понятен, даже если этот флоу не делегируем
  сегодня.

Позиция сессии (проверяется макетами, не решение):

- Платформа мульти-флоу остаётся на `/flows`: каждый флоу триггерится со своей
  страницы, как сегодня. **Делегирование — свойство флоу** (ест бэклог-тикеты
  автономно, выдаёт PR), а не свойство платформы. Сегодня такой флоу один —
  Developer Factory; Test Factory интерактивный (одна стори, QA-гейты), его вход —
  страница флоу → Trigger flow.
- Инбокс Tasks называет свой флоу/скоуп/спринт явно (карточка «Delegation scope» в
  шапке). При появлении второго делегируемого флоу тот же экран поглощает его
  секцией по флоу — без новой навигации и generic-механизма (постулат: мульти-флоу
  только при реальном втором флоу).
- Цены: A — правки шаблонов + `FLOW_ID`→конфиг (минимум); B — переработка
  presentation-слоя, риск двух admission-путей поверх одной стейт-машины;
  C — параллельность ломает серийный queue (спека: один активный task), мульти-флоу
  генерализация преждевременна.

Артефакты: [`../mockups/tasks-inbox-v1.html`](../mockups/tasks-inbox-v1.html) —
инбокс сегодня, один делегируемый флоу, все ключевые состояния строк;
[`../mockups/tasks-inbox-v1-two-flows.html`](../mockups/tasks-inbox-v1-two-flows.html) —
стресс-вариант того же экрана с двумя делегируемыми флоу (справочный, реализации не
требует).

Реакция оператора (2026-10-25, дословно): «Не то, обсуждаем вход». Инбокс
(глобальный список + «делегирование — свойство флоу» в карточке скоупа) не отвечает
ментальной модели мульти-флоу даже со стресс-вариантом. Вывод: вход должен быть
организован от флоу, а не от глобального списка задач. Макет инбокса остаётся в
репо как отвергнутое направление.

Открытый вопрос для следующего шага: flow-центричный вход — (а) секция делегирования
появляется на странице флоу, когда флоу умеет автономную работу над бэклогом
(в M1 только dev-factory), или (б) делегирование для Test Factory делается реальным
вторым флоу в этой же переделке (расширение скоупа).

**Решение (2026-10-25, оператор — вариант «флоу-вход, способность»):**

- Вход в делегирование — **страница флоу**: у флоу, способного автономно работать
  над бэклогом, на его странице появляется секция «Sprint work» (скоуп → задачи →
  выбор → запуск). В M1 такой флоу один — Developer Factory.
- Test Factory остаётся интерактивной: её страница сегодня без секции, вход —
  обычный Trigger flow. Секция появляется, когда флоу получит способность
  (отдельная продуктовая работа, не эта переделка).
- Глобальный пункт Tasks уходит из навигации; admission-путь остаётся один,
  core не трогается; `FLOW_ID` в `PilotExecutionLauncher.java:35` → свойство
  конфига (остаётся кандидатом в переделку).
- Цена: перенос пилотного presentation-слоя под страницу флоу (роуты вида
  `/flows/dev-factory/tasks`, шаблоны, ссылки) — без изменений стейт-машины.

Артефакт: [`../mockups/flow-sprint-work-v1.html`](../mockups/flow-sprint-work-v1.html)
— страница `/flows/dev-factory` с секцией «Sprint work», реальный pipeline из
дескриптора ниже без изменений; в макете помечен открытый вопрос «Rescan now vs
авто-поллинг» (пункт 2 плана сессии). Ждём реакции оператора по содержанию секции.

Открытые вопросы по п.1 (переносится в п.2 плана сессии): ручной рескан vs только
авто-поллинг; судьба деталей задачи (маршрут полного списка и деталировка под флоу);
кросс-ссылки с дашборда.

## 2. Деталь задачи: представление результата

**Статус: макет показан (2026-10-25), ждём реакции оператора.**

Текущий `pilot-task.html` уже закрывает большую часть спеки 6.2 (заголовок с ключом
Jira и состоянием, Result + Retry с объяснением, стоимость, таблица попыток,
технические детали свернуты). Отсутствует обязательный блок спеки 6.2 — поэтапная
evidence последней попытки (Preparation / Implementation / Verification /
Publication с Passed / Failed / Not run и ссылками на артефакты).

Макет [`../mockups/task-detail-v1.html`](../mockups/task-detail-v1.html) (пример —
остановленная задача с ретраем):

- обратная ссылка «← Developer Factory · Sprint work» (вместо глобального
  `/tasks`);
- Result-предложение по образцу спеки: причина одним языком + «No PR was created» +
  кумулятивная стоимость с пометкой неполноты + явный следующий шаг (Retry или
  продолжить в своём инструменте);
- «What happened (last attempt)» — новый блок: четыре стадии, Passed/Failed/Not
  run, ссылки на Surefire-отчёты и лог попытки;
- Attempts: две попытки (initial via manual selection + retry), кумулятив $1.45;
- Cost and usage: полный разброс токенов спеки 6.3 (input/output/cache-read/
  cache-write), incomplete-пометка, модель.

Цена реализации: один новый блок карты в шаблоне + данные, которые уже пишет
движок (стадии попытки известны); маршрут детали — под флоу.

**Реакция оператора на v1 (2026-10-25, дословно):** «пока это конечно выглядит не
хорошо, скомкано, поанализируй сам картинку, нужно понять какие элементы должны
быть на экране».

Анализ v1 (измерения в браузере, не глаз):

- Вертикальный ритм отсутствовал: межсекционные отступы 24 → 16 → **0** → **0** →
  8px — контент не был обёрнут в `.stack` (компонент приложения, `gap: 1.5rem`).
- Иерархии не было: четыре примерно равные карты (220/338/278/292px), результат —
  самое важное — выглядел обычным текстом 14px в 3 строки.
- Таблица попыток: 7 колонок, ячейки в ~4 строки (высота строки 89px).
- Evidence стадий таблицей — разреженно, не таймлайн.

Инвентарь элементов экрана детали (утверждается с v2):

| Зона | Элементы | Зачем |
| --- | --- | --- |
| Идентификация | заголовок; ключ Jira (ссылка); бейдж состояния; destination | «что это за работа» |

## 3. Страница флоу: Sprint work v2 (takeover)

**Статус: макет готов к показу (2026-10-26), ждём реакции оператора.**

Ориентир — ментальная модель оператора дословно (журнал недопониманий п. 3):
«кнопка "просканировать джиру" на странице флоу → выбор задач → trigger-flow после
выбора». v1 её не отражал: сканирование спрятано в третьей строке карточки рядом с
бейджем «open question», главная кнопка шапки — `Trigger flow` (JSON-диалог,
`/flows/{id}/trigger`), т.е. второй путь запуска в обход идентичности задач пилота
(противоречит решению п. 1 «admission-путь один»); таблица смешивает «что можно
запустить» и «что произошло» — пустые ячейки чекбоксов у половины строк; на 1440px
строки 67–110px («12 minutes ago» в 3 строки, репозиторий в 2).

Словарь экрана — в терминах оператора: **Available** (найдено в спринте, не
запускалось) → **Trigger flow for N tasks** → **Triggered** (флоу запущен: в очереди,
работает, результат). Это та же операция, что `Run selected` в спеке 4.2 — меняется
подпись, не механика.

## 4. Скоуп скана Jira: что сканируется и где это настраивается

**Статус: обсуждается (2026-10-26).**

Вопрос оператора (дословно): «кнопка удобная, а по каким фильтрам он сканит, где они
настроены, как их конфигурировать, тоже есть большой вопрос».

Факты (код и шаблон окружения):

- Скоуп целиком задаётся переменными в `.env` (копия `.env.pilot.example`):
  `FACTORY_PILOT_SOURCE` (борда или saved filter, URL/ID; обязательно),
  `FACTORY_PILOT_SPRINT_ID` (обязательно), `FACTORY_PILOT_STATUSES` (обязательно,
  по умолчанию `"To Do"`), опционально `FACTORY_PILOT_ASSIGNEE`,
  `FACTORY_PILOT_PROJECTS`, `FACTORY_PILOT_LABEL`. Изменение — правка `.env` и
  `docker compose up -d` (пересоздаёт контейнер; скоуп не входит в fingerprint
  рантайма, поэтому повторная проверка рантайма не нужна). Исправлено 2026-10-26:
  в первом ответе оператору здесь ошибочно стоял `scripts/start-pilot.sh`.
- Итоговый запрос собирает `PilotScopeResolver.compose`:
  `sprint = <id> AND status in (...) AND (<JQL фильтра борды>)` плюс опциональные
  `assignee`, `project in (...)`, `labels`; `ORDER BY` берётся из фильтра борды.
- Sprint id ищется руками: из URL бэклога (`?agileSprintID=`) или curl к agile API
  (инструкция в `.env.pilot.example`). Меняется каждый спринт.
- Маршрут «проект Jira → репозиторий» — `config/developer-repositories.yaml`
  (`jira-projects: [...]` у каждого репозитория); разрешение публиковать — env-флаги
  `*_DELIVERY_AUTHORIZED`.
- В UI скоуп виден только строкой в шапке `/tasks` (источник, спринт, статусы,
  ограничения); `/developer/configuration` скоуп пилота не показывает вовсе;
  итоговый JQL нигде не виден.
- Смена скоупа (в т.ч. спринта) меняет fingerprint и уже сегодня снимает
  автоматический режим с возвратом в Review before run (спека 4.2).

Прозрачность (во всех вариантах, нарисовано в `flow-sprint-work-v2.html`):
раскрывашка «What exactly is scanned» в карточке спринта — источник и его фильтр,
что добавляет Factory, итоговый запрос, ссылка «Open this search in Jira» (тот же JQL
в поиске Jira), где менять. Цена: шаблон + 3–4 правила CSS + ссылка
`<jira>/issues/?jql=<encoded>`.

Варианты «где менять»:

- **A — как сегодня:** всё в `.env` + `scripts/start-pilot.sh`. Цена: ноль. Боль:
  каждый спринт искать новый id и перезапускать.
- **B — спринт берётся активный с борды автоматически (рекомендация),** остальное в
  `.env`. Цена: метод коннектора `GET /rest/agile/1.0/board/{id}/sprint?state=active`
  (~25 строк + WireMock-тест), `FACTORY_PILOT_SPRINT_ID` становится необязательным
  (явный id побеждает). Смена спринта = смена скоупа → автоматический режим снимается
  существующей логикой. Ограничения: источник — saved filter без борды или у борды
  два активных спринта → понятная ошибка «укажите `FACTORY_PILOT_SPRINT_ID`».
  Отступление от спеки: «automatic sprint rollover» там отложен.
- **C — весь скоуп редактируется на странице:** форма + хранение + валидация, вторая
  точка конфигурации поверх env. Это «динамическая конфигурация» из журнала
  недопониманий п. 4, которую решили вынести в отдельный майлстоун.

## 5. `scripts/start-pilot.sh`: нужен ли отдельный скрипт запуска

**Статус: обсуждается (2026-10-26).**

Претензия оператора (дословно): «зачем нужен этот скрипт? scripts/start-pilot.sh — это
похоже на слоп очередной, я хочу запускать командой docker compose up -d, как это было
сделано».

Факты:

- Происхождение: спека 3.1 требовала «one documented Factory start action» с явно
  раскрытой платной проверкой модели; план S11 (утверждён) прямо назвал форму —
  «Create .env.pilot.example and scripts/start-pilot.sh». Т.е. не самовольный слой, но
  форма «shell-скрипт + POST» выбрана планом, а не продиктована спекой.
- Что делает скрипт (44 строки): проверяет наличие `.env`; `docker compose up -d
  --build`; ждёт `/actuator/health`; печатает `GET /api/pilot/status`; вызывает
  `POST /api/pilot/start`; печатает итог.
- `docker compose up -d` уже поднимает весь стек (postgres, coding-runtime, factory) и
  пробрасывает все `FACTORY_PILOT_*`. README уже говорит: после правки `.env` —
  `docker compose up -d`.
- Единственная работа, которую без скрипта никто не делает, — `POST /api/pilot/start`:
  живые проверки + одна маленькая платная «smoke»-проверка модели из coding-контейнера.
  Без неё `PilotReadinessGate` блокирует запуск задач («run the pilot start action
  first»), discovery при этом работает.
- Проверка привязана к fingerprint рантайма (образ, модель, endpoint, тип и хэш
  креденшела, лимиты smoke, инструкции). Перезапуск без смены рантайма и смена скоупа
  Jira её не требуют; первый запуск и смена модели/прокси/образа — требуют.

Варианты (в обоих скрипт удаляется, запуск — только `docker compose up -d`):

- **A — проверка по кнопке в UI.** Пока рантайм не проверен, на странице флоу баннер
  «Execution is blocked: runtime check has not run» + кнопка «Run runtime check» с
  раскрытием «одна маленькая платная проверка модели». Платный вызов остаётся явным
  (как в спеке). Цена: удалить скрипт, поправить README/`.env.pilot.example`, баннер +
  форма на существующий `PilotStartupService.start()`.
- **B — проверка сама при старте приложения (рекомендация).** Если fingerprint
  рантайма изменился, Factory запускает проверку сама после старта; страница флоу
  показывает итог («Runtime check passed 10:02 · $0.004») или красный баннер с
  причиной и кнопкой «Check again». Цена: то же + запуск `start()` после
  `ApplicationReadyEvent` в фоне. Отступление от спеки: платный вызов (центы, только
  при смене рантайма) происходит без отдельного клика, но виден на странице.
- Вне вариантов: убрать проверку целиком (первая задача сама покажет поломку
  рантайма, спека 5.3 уже ставит общую паузу при отказе провайдера) — это вырезание
  машинерии S11, отдельный разговор.

Это не UX-решение в чистом виде, но баннер готовности — состояние страницы флоу
(пункт очереди 4), а удаление скрипта — работа сессии «спека и переделка».

**Решение (2026-10-26, оператор, дословно):** «не надо проверять рантайм, он и так
нормально запустится, убери этот слоп в виде скрипта». Ни A, ни B: проверка рантайма
убирается целиком, запуск — только `docker compose up -d`.

Объём удаления (проверено по коду): удалить только файл нельзя — `PilotReadinessGate`
(`PilotExecutionLauncher.java:102`, `readiness.requireExecutionReady()`) без пройденной
проверки блокирует каждый запуск задачи, т.е. пилот перестанет запускать работу.
Уходит вся машинерия S11: `scripts/start-pilot.sh`; пакет `pilot/startup` (725 строк:
`PilotStartupService`, `PilotRuntimeSmoke`, `PilotRuntimeIdentity`, `RuntimeFingerprint`,
`PilotReadinessGate`, `PilotExecutionReadiness`, `PilotReadiness`,
`PilotStartupProperties`); `PilotStartupController` (`/api/pilot/start`,
`/api/pilot/status`); `PilotReadinessEvidence` + репозиторий (таблица V9 — новой
миграцией удаления, старые миграции не правятся); свойства и env
`FACTORY_PILOT_SMOKE_*`; разделы README и `.env.pilot.example`; тесты
`PilotStartupTest`, `PilotRuntimeSmokeTest`, `PilotStartupControllerTest` и моки гейта
в шести интеграционных тестах.

Предложение по умолчанию (оператор может возразить): оставить одну дешёвую защиту —
если включена очистка истории (`FACTORY_RETENTION_ENABLED=true`), пилотное исполнение
не стартует с понятной ошибкой в логе, потому что очистка стирает попытки и их
стоимость. Требование rate card уходит: без тарифа стоимость показывается как Unknown,
спека 6.3 это допускает.

Где делать: это код, а не дизайн; варианты — отдельной сессией параллельно с
UX-сессией или здесь, с паузой дизайна.
