## 1. Входная точка: где оператор начинает делегирование

**Статус: решено (2026-10-25) — flow-центричный вход, делегирование — способность флоу.**

Оператору предложены три варианта входа: A — Tasks-инбокс (единственная рабочая
поверхность, флоу/скоуп/спринт названы в шапке, ссылки с дашборда и страницы флоу);
B — вход на странице флоу (кнопка сканирования + выбор задач на `/flows/dev-factory`);
C — хелпер-лаунчер, запускающий задачи параллельно/последовательно.

Оператор вариант не выбрал и переформулировал проблему (дословно): «Так просто и не
ответить. Надо вот это и обсуждать… Вот как будет выглядеть task inbox? …у нас же
условно платформа может содержать несколько разных flow. Это логично и понятно. То
есть, если я, например, выберу тест флоу для выполнения спринта, я тестировщик. Я
хочу запустить работу для своего флоу. Что мне делать?»

Зафиксированные требования из ответа:

- Решение о входной точке — только после визуального рассмотрения инбокса
  («порисовать»), не в абстракции.
- Дизайн обязан отвечать на ментальную модель «платформа = много флоу»: путь
  тестировщика со своим флоу должен быть понятен, даже если этот флоу не делегируем
  сегодня.

Позиция сессии (проверяется макетами, не решение):

- Платформа мульти-флоу остаётся на `/flows`: каждый флоу триггерится со своей
  страницы, как сегодня. **Делегирование — свойство флоу** (ест бэклог-тикеты
  автономно, выдаёт PR), а не свойство платформы. Сегодня такой флоу один —
  Developer Factory; Test Factory интерактивный (одна стори, QA-гейты), его вход —
  страница флоу → Trigger flow.
- Инбокс Tasks называет свой флоу/скоуп/спринт явно (карточка «Delegation scope» в
  шапке). При появлении второго делегируемого флоу тот же экран поглощает его
  секцией по флоу — без новой навигации и generic-механизма (постулат: мульти-флоу
  только при реальном втором флоу).
- Цены: A — правки шаблонов + `FLOW_ID`→конфиг (минимум); B — переработка
  presentation-слоя, риск двух admission-путей поверх одной стейт-машины;
  C — параллельность ломает серийный queue (спека: один активный task), мульти-флоу
  генерализация преждевременна.

Артефакты: [`../mockups/tasks-inbox-v1.html`](../mockups/tasks-inbox-v1.html) —
инбокс сегодня, один делегируемый флоу, все ключевые состояния строк;
[`../mockups/tasks-inbox-v1-two-flows.html`](../mockups/tasks-inbox-v1-two-flows.html) —
стресс-вариант того же экрана с двумя делегируемыми флоу (справочный, реализации не
требует).

Реакция оператора (2026-10-25, дословно): «Не то, обсуждаем вход». Инбокс
(глобальный список + «делегирование — свойство флоу» в карточке скоупа) не отвечает
ментальной модели мульти-флоу даже со стресс-вариантом. Вывод: вход должен быть
организован от флоу, а не от глобального списка задач. Макет инбокса остаётся в
репо как отвергнутое направление.

Открытый вопрос для следующего шага: flow-центричный вход — (а) секция делегирования
появляется на странице флоу, когда флоу умеет автономную работу над бэклогом
(в M1 только dev-factory), или (б) делегирование для Test Factory делается реальным
вторым флоу в этой же переделке (расширение скоупа).

**Решение (2026-10-25, оператор — вариант «флоу-вход, способность»):**

- Вход в делегирование — **страница флоу**: у флоу, способного автономно работать
  над бэклогом, на его странице появляется секция «Sprint work» (скоуп → задачи →
  выбор → запуск). В M1 такой флоу один — Developer Factory.
- Test Factory остаётся интерактивной: её страница сегодня без секции, вход —
  обычный Trigger flow. Секция появляется, когда флоу получит способность
  (отдельная продуктовая работа, не эта переделка).
- Глобальный пункт Tasks уходит из навигации; admission-путь остаётся один,
  core не трогается; `FLOW_ID` в `PilotExecutionLauncher.java:35` → свойство
  конфига (остаётся кандидатом в переделку).
- Цена: перенос пилотного presentation-слоя под страницу флоу (роуты вида
  `/flows/dev-factory/tasks`, шаблоны, ссылки) — без изменений стейт-машины.

Артефакт: [`../mockups/flow-sprint-work-v1.html`](../mockups/flow-sprint-work-v1.html)
— страница `/flows/dev-factory` с секцией «Sprint work», реальный pipeline из
дескриптора ниже без изменений; в макете помечен открытый вопрос «Rescan now vs
авто-поллинг» (пункт 2 плана сессии). Ждём реакции оператора по содержанию секции.

Открытые вопросы по п.1 (переносится в п.2 плана сессии): ручной рескан vs только
авто-поллинг; судьба деталей задачи (маршрут полного списка и деталировка под флоу);
кросс-ссылки с дашборда.

## 2. Деталь задачи: представление результата

**Статус: макет показан (2026-10-25), ждём реакции оператора.**

Текущий `pilot-task.html` уже закрывает большую часть спеки 6.2 (заголовок с ключом
Jira и состоянием, Result + Retry с объяснением, стоимость, таблица попыток,
технические детали свернуты). Отсутствует обязательный блок спеки 6.2 — поэтапная
evidence последней попытки (Preparation / Implementation / Verification /
Publication с Passed / Failed / Not run и ссылками на артефакты).

Макет [`../mockups/task-detail-v1.html`](../mockups/task-detail-v1.html) (пример —
остановленная задача с ретраем):

- обратная ссылка «← Developer Factory · Sprint work» (вместо глобального
  `/tasks`);
- Result-предложение по образцу спеки: причина одним языком + «No PR was created» +
  кумулятивная стоимость с пометкой неполноты + явный следующий шаг (Retry или
  продолжить в своём инструменте);
- «What happened (last attempt)» — новый блок: четыре стадии, Passed/Failed/Not
  run, ссылки на Surefire-отчёты и лог попытки;
- Attempts: две попытки (initial via manual selection + retry), кумулятив $1.45;
- Cost and usage: полный разброс токенов спеки 6.3 (input/output/cache-read/
  cache-write), incomplete-пометка, модель.

Цена реализации: один новый блок карты в шаблоне + данные, которые уже пишет
движок (стадии попытки известны); маршрут детали — под флоу.

**Реакция оператора на v1 (2026-10-25, дословно):** «пока это конечно выглядит не
хорошо, скомкано, поанализируй сам картинку, нужно понять какие элементы должны
быть на экране».

Анализ v1 (измерения в браузере, не глаз):

- Вертикальный ритм отсутствовал: межсекционные отступы 24 → 16 → **0** → **0** →
  8px — контент не был обёрнут в `.stack` (компонент приложения, `gap: 1.5rem`).
- Иерархии не было: четыре примерно равные карты (220/338/278/292px), результат —
  самое важное — выглядел обычным текстом 14px в 3 строки.
- Таблица попыток: 7 колонок, ячейки в ~4 строки (высота строки 89px).
- Evidence стадий таблицей — разреженно, не таймлайн.

Инвентарь элементов экрана детали (утверждается с v2):

| Зона | Элементы | Зачем |
| --- | --- | --- |
| Идентификация | заголовок; ключ Jira (ссылка); бейдж состояния; destination | «что это за работа» |
| Ответ | исход одним предложением (причина, был ли PR, следующий шаг); чипы: кумулятивная стоимость+неполнота, попытки, активное время, модель; действия: Retry / Open in Jira | «что случилось и что делать» — доминирует визуально |
| Evidence последней попытки | стрип 4 стадий существующим компонентом `developer-stages` (done/failed/not run + длительность); под провалом — упавшие проверки и ссылки (отчёты, лог, артефакты) | «докажи» |
| История попыток | компактная таблица 5 колонок: №/тип/via, состояние+run, когда+активное время, результат, стоимость | «сколько раз и почём» |
| Токеномика | полный разброс токенов (input/output/cache), модель, incomplete-пометки | релизный гейт 6.3 |
| Тех. детали | свёрнуто: task id, проект, engine runs | диагностика |

Не на этом экране: скоуп спринта и режим admission (страница флоу), выбор задач,
синхронизация.

Артефакт v2: [`../mockups/task-detail-v2.html`](../mockups/task-detail-v2.html)
— проверено в браузере: отступы всех секций ровно 1.5rem, стадии рендерятся
компонентом консоли, попытки 5 колонок (строка 71px). v1 остаётся в репо для
сравнения.
