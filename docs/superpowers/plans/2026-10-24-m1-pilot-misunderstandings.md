## 1. Зачем Jira-креды (email + API token)? Раньше работало без ключа — просто ссылка на тикет и ключ проекта. Это сильное усложнение конфигурации.

**Статус: обсуждено (2026-10-24).**

Проверенные факты (живые пробы + код ветки):

| Jira endpoint | Анонимно | Для чего |
|---|---|---|
| `GET /rest/api/2/issue/{key}` | 200 OK | прочитать один известный тикет |
| `POST /rest/api/2/search/jql` | 200 OK | финальный поиск задач в discovery |
| `GET /rest/agile/1.0/board/{id}/filter` | **401** (проверено) | board → сохранённый фильтр → JQL скоуп |
| `GET /rest/agile/1.0/sprint/{id}` | **401** (agile API) | определить спринт в скоупе |

- `JiraProperties.isReadable()` = только baseUrl; анонимный режим чтения в коннекторе есть
  (записи запрещены). Креды нужны не «просто так».
- Старый Developer Flow (origin/main) читал только один тикет по ссылке — это работает
  анонимно. Пилот же сам находит задачи: board/saved-filter + **sprint** + статусы. Шаги
  board и sprint идут через agile API Atlassian, который не отдаётся анонимно даже на
  открытом сайте — ограничение платформы Atlassian, не наш архитектурный выбор.
- Решение «обязательный sprint в скоупе» зафиксировано в плане (Global Constraints:
  «one explicit sprint», «Sprint and eligible statuses are required») — то есть это
  утверждённое решение, а не самовольное.
- Фрикшн-находка: `.env.pilot.example` требует email/token, но `scripts/start-pilot.sh`
  их **не проверяет** — без кредов стек стартует, а discovery падает позже малопонятным 401.

Вывод: требование кредов — внешнее ограничение Atlassian (agile API), вызванное сменой
источника задач (автономный discovery вместо ссылки на тикет). Само требование — из
утверждённого плана.

Открытые вопросы:
1. Принять email+token как цену автономного discovery — или пересматривать скоуп
   (спринт сейчас обязателен, saved-filter без спринта всё равно требует agile API).
2. Добавить fail-fast проверку Jira-кредов в старт скрипта (readiness check) вместо
   позднего 401.

## 2. Система, которая должна быть простой и легко поддерживаемой, с каждой фичей становится сложнее — «каждая фича добавляет новый слой нейрослопа». Как с этим жить и как не допустить дальше?

**Статус: обсуждено (2026-10-25).**

Проверенные факты (git-статистика ветки vs план/спека):

| Отрезок | Основной код (src/main) |
|---|---|
| Вся ветка над `main` | 428 файлов, +52 781 / −515 (включая доки/конфиг) |
| Dev-factory майлстоун (`main..8bc14f3`) | 242 файла, +16 721 / −9 232 |
| M1 пилот (`8bc14f3..21a952f`) | 91 файл, +6 697 / −113; тесты +9 179 |

- M1 по модулям: factory-app +4 921 (UI-экраны S10, readiness S11, проекция S09),
  dev-factory Java +755, connectors +470 (Jira discovery S01), core +57.
  Сейчас: factory-app 84 файла / 9,6k строк, dev-factory 66 / 7,9k, core 60 / 4,3k.
- Пилот = 41 класс в шести подпакетах (`source/persistence/admission/execution/startup/presentation`)
  — это дословно файловая карта из плана (план, строка 82: «New pilot code lives together
  under APP/pilot, divided only where responsibilities justify it: source, persistence,
  admission, execution, startup and presentation»).
- План явно запрещал спекулятивные слои (строка 103: no speculative plugin registry,
  generic workflow DSL, generic event bus) и god-service (строка 100: «Do not build a
  single PilotService») — код это соблюдает: нет DSL/шины/реестра, сущности маленькие.
- Ни один план майлстоуна до сих пор не содержит секции «что удаляем/упрощаем» —
  оба плана только добавляют. Единственное крупное удаление (−9,2k в dev-factory
  майлстоуне) — рефакторинг собственных добавок внутри того же майлстоуна.
- Часть роста — цена одобренных требований, не слоп: «friendly, readable UI» —
  релизный гейт спеки (план, строка 17); тесты на реальной персистентности —
  конвенция (строка 104).

Вывод: атрибуция иная, чем «модель обросила слоями сама». Структура слоёв M1
одобрена планом дословно; запрет на спекулятивную общность модель соблюла.
Реальная системная проблема: формат планирования только наращивает — планы пишутся
моделью, оператор утверждает, «нейрослоп» входит в систему в момент утверждения
плана, а не в момент кодинга. Контрольная точка — ревью планов, и в ней нет
инструмента «а что этот план удаляет?».

Решение (2026-10-25, оператор):
- **Отклонено:** обязательная секция «что удаляем/упрощаем» в планах и метрика-храповик
  (меры 1–2 исходного предложения) — оператор не хочет формализма: строгие планы вредны,
  агент должен понимать «не пишем новые слои слопа» как постоянный принцип, а не как
  графу шаблона.
- **Отклонено:** отдельный simplification-майлстоун (мера 3) — это ровно та доп. работа,
  которой оператор хочет избежать; принцип — «сразу делаем вдумчиво», а не переделываем.
- **Принято:** качество закладывается на стадии планирования (планирование — важнейшая
  стадия): план обязан предлагать минимальную версию, расширение существующих структур
  вместо новых слоёв.
- **Принято:** ревью критиками в саб-агентах — в т.ч. на стадии ревью планов
  (свежий контекст, вопрос «какой слой добавляется и зачем»).

Follow-up задача (вне этой сессии, по явному заданию): короткая правка AGENTS.md
(«How to work») — принцип anti-layer на стадии планирования: каждый новый пакет/слой
в плане требует явного оправдания; по умолчанию расширяем существующее и берём
минимальную версию. Без формальных секций и метрик.

Дополнение (2026-10-25, оператор, при закрытии сессии): той же правкой добавить в
AGENTS.md главную философию/постулаты проекта — «просто, прозрачно, легко
конфигурируемо» — как фильтр для дизайна всех последующих фич.

**Исполнено (2026-10-25, команда оператора «уже можно поменять»):** в AGENTS.md
добавлены секция «Product postulates» (simple/transparent/easy to configure,
стоимость слоёв и конфиг-поверхности явна в плане) и три правила в «How to work»:
лестница начинается с планирования (минимальная версия, расширение существующего,
оправдание каждого нового слоя), макет в репо до утверждения плана для UI-фич,
adversarial-проход саб-агента-критика до имплементации. Не закоммичено — коммит
по команде оператора.

Оговорка (зафиксирована): принцип — перспективный; накопленный объём (≈24k строк
основного кода) сам от этого не уменьшится. Существующая в AGENTS.md lean-code-правка
на код-стадии («the best code is the code you never wrote») роста не остановила —
она не была привязана к стадии планирования; отсюда акцент решения именно на план
и на критиков в ревью.

Открытые вопросы: нет.

## 3. Плохо оговорённый UI до начала работы: (а) «оказался новый пункт меню Tasks», ожидалась flow-центричная схема — триггерим флоу → внутри выбираем задачи; (б) «сам UI уродливый и не продуманный, много слопа» — нужны были макеты и обсуждение до имплементации. Note: ожидал кнопку «просканировать джиру» на странице флоу и trigger-flow после выбора.

**Статус: обсуждено (2026-10-25).**

Проверенные факты:

- **UX-модель целиком в утверждённой спеке, дословно.** Спека (строки 15, 28, 67):
  «select matching Jira tasks on the dashboard and press **Run selected**»;
  «task checkboxes, Run selected and Retry are operational controls»;
  сценарий первого использования — «Open the dashboard… select suitable ones and
  press Run selected». Flow-центричной схемы (триггер флоу → выбор задач в HITL)
  нет нигде в спеке и плане. Пункт меню Tasks запланирован явно: план S10 —
  «Modify RES/templates/fragments/layout.html navigation», `/tasks` + `/tasks/{taskId}`,
  а `/executions` сохранён как техническое/легаси-представление.
- **Автодискавери вместо кнопки «сканировать» — тоже из спеки.** Спека 4.1 (строка 132):
  «Poll every five minutes while discovery is enabled». Реализовано ровно так:
  `PilotDiscoveryPoller` — `@Scheduled` c `poll-interval-ms:300000` по умолчанию;
  кнопки ручного сканирования нет ни в спеке, ни в UI (на `/tasks` — «last full sync»
  и блокер при неполной синхронизации).
- **Макетов в репозитории нет.** Спека дважды ссылается на «browser mockups»
  (строка 9: «The browser mockups illustrate the direction»; строка 277: «Mockups
  remain references for typography and hierarchy»), но файлов макетов в `docs/` нет —
  найти невозможно. При этом «exact mockup reproduction» явно отложена (строка 52),
  т.е. макеты не были обязательством. Эстетику оценивал сам модельный контур:
  S10, шаг 6 — свой browser-проход со скриншотами в `/tmp` (не сохранены) +
  саб-агент-критик «ACCEPT WITH FIXES». Оператор не видел ни одного макета до
  готового UI.
- **Технические вопросы оператора:** задачи с борды без ключа — нельзя
  (agile API 401 анонимно, см. пункт 1); LLM для discovery не нужна — спека
  (строка 134): «Discovery does not perform paid planning, coding or AI eligibility
  analysis», реализовано детерминированным коннектором (S01, +470 строк в
  `factory-connectors`, без ChatClient). Коннекторы искать и получать задачи умеют.

Вывод: **(а) — не самовольное решение.** Таск-центричная модель (Tasks + галочки +
Run selected + фоновый discovery) — дословно утверждённая спека; ожидание оператора
(flow-центричный триггер с HITL-выбором и кнопкой сканирования) в спеке отсутствовало
с самого начала. Частично ожидание совпадает с сделанным: выбор галочками + запуск
выбранного есть. Расхождение — только входная точка (отдельный экран Tasks vs
страница флоу) и ручной скан vs автополлинг.
**(б) — претензия к процессу справедлива.** Оператор утверждал UI в виде прозы,
без единого видимого макета; спека сама легализовала отсутствие визуального
обязательства («exact mockup reproduction» deferred, макеты «не требования»).
В результате визуальное качество никто не мог проконтролировать до готового кода —
ни оператор, ни внешний артефакт; «уродливость» не обсуждалась ни на одной стадии.

Предлагаемые решения (вынесены оператору):
- Признать: расхождение UX-модели — не ошибка реализации, а несовпадение ожидания
  оператора с текстом утверждённой им спеки; визуальное качество не проектировалось
  вовсе — это процессный провал, закрывается правилом ниже.
- Правило (развитие пункта 2 журнала): фича с UI не идёт в план без макета —
  статический HTML/скриншот-макет лежит в репо рядом со спекой, оператор смотрит
  его до утверждения плана; «точное воспроизведение» не нужно, нужно согласованное
  направление.
- Текущий `/tasks` UI: переделка — отдельная задача по явному заданию (макеты →
  утверждение → правка шаблонов; входная точка Tasks vs flow-страница решается
  в той же задаче).

Решение (2026-10-25, оператор):
- **Правило «макет до плана» подтверждено** («да, хороший план»).
- Переделка UI не решается на месте: UX требует отдельной проработки — см. 3.1.

### 3.1. Продолжение: как должна быть устроена входная точка (диалог с экспертом)

**Статус: закрыт (2026-10-25) — решение вынесено в отдельную UX-сессию.**

Оператор подтвердил правило «макет до плана» (п.1 предложений) и открыл обсуждение
входной точки: «может пусть будет Tasks, это просто "упрощалка-страница", а она под
капотом просто вызывает developer-flow? но флоу может быть много, почему именно
девелопер-флоу? может другие флоу — написания тестов, дев-фронтенд и т.д.»

Проверенные факты:

- Привязка пилота к флоу — константа `FLOW_ID = "dev-factory"` в
  `PilotExecutionLauncher.java:35`; конфигурируется только вкл/выкл discovery/execution
  (`application.yaml:128+`).

Позиция, вынесенная оператору:

- Tasks — не «страница девелопер-флоу», а **инбокс делегированной работы**. UX осмыслен
  только для флоу, которые едят бэклог-тикеты как единицы работы, работают автономно и
  выдают PR; вся машинерия пилота (discovery/attempts/authority) спроектирована под это.
  Девелопер-флоу — единственный такой флоу сегодня, не «выбранный из многих».
- Test Factory интерактивная (один стори на входе, QA-гейты) — её вход уже есть на
  странице флоу; делегирование для неё — отдельный продуктовый дизайн, не галочка.
- Мульти-флоу, когда появится реально: flow id из константы → поле конфига скоупа
  (одно свойство + бейдж в шапке Tasks); никакого generic-механизма (принцип пункта 2).
- Пикер задач на странице флоу как основной вход — отклонён: раздваивает admission
  на два UI-пути поверх одного стейт-машины. Ментальную модель оператора закрывают
  связи: дашборд/страница флоу → ссылка «Delegate sprint work → /tasks»; шапка Tasks
  явно называет флоу+скоуп+спринт.

Предлагаемый экшен айтем (расширяет задачу переделки UI из п.3):
1. Макеты: Tasks как work inbox, шапка называет флоу/скоуп/спринт явно.
2. Кросс-ссылки: дашборд и `/flows/dev-factory` → `/tasks`; admission-путь один.
3. В той же задаче: `FLOW_ID`-константа → свойство конфига (дефолт `dev-factory`).

Открытые вопросы: оператор подтверждает три пункта айтема — или настаивает на
пикере на странице флоу как основном входе.

**Решение (2026-10-25, оператор):** три пункта айтема НЕ утверждаются здесь — сам UX
требует отдельной проработки до любых решений. Дословно: «надо где-то в отдельной
сессии прям обсудить, проработать, понять, иметь clear vision насчет того, как это
будет выглядеть. То есть это отдельная страница, или это страница flows, это внутри
flow, или это какой-то хелпер, который будет запускать эти flow в параллели или
последовательно, это уже другая задача как это сделать не усложняя, как, добавив
минимум, можно получить максимум профита/импакта, не переписывая опять весь кор
и не ломая ничего».

**Экшен айтем: отдельная UX-сессия по входной точке пилота.** Входные материалы —
анализ и рекомендации выше (инбокс делегированной работы, один admission-путь,
`FLOW_ID`-константа как кандидат в конфиг, мульти-флоу только при реальном втором
флоу). Ограничения сессии: минимум изменений, максимум импакта, без переписывания
core и без поломок; правило «макет до плана» (п.3) действует и там. Статус 3.1 —
закрыт: решение вынесено в отдельную задачу.

## 4. Сложность конфигурации: «разработчик, который хочет просто использовать Claude Code без настройки, должен идти и что-то настраивать — это сложно». Возможно, динамическая конфигурация или отдельный майлстоун.

**Статус: обсуждено (2026-10-25) — зафиксировано как риск, вердикт не выносился.**

Оператор оговорил явно: это не претензия («я пока не настраивался, это даже не
консерв, просто ощущения»), а кандидата в будущую повестку.

Проверенные факты (поверхность конфигурации):

- `.env.pilot.example` — 20 переменных для пилотного пути запуска.
- `factory-app/src/main/resources/application.yaml` — 99 уникальных env-плейсхолдеров
  `${...}`.
- README, таблица конфигурации — 39 строк.
- Плюс известный фрикшн из пункта 1: `start-pilot.sh` не проверяет Jira-креды,
  стек стартует без них и падает позже малопонятным 401.

Контекст по спеке: «Simple first use» — один из четырёх обязательных релизных гейтов;
при этом «General configuration through the UI» спека явно отложила (optional/deferred),
а M1 закрыл «первый запуск» scripted-путём S11 (одна startup-операция с readiness),
не уменьшая саму поверхность переменных.

Вывод: не атрибуция конкретного решения, а системный риск по гейту «Simple first
use»: поверхность конфигурации росла вместе с функциональностью, «настройка за

от нуля (оператор ещё его не проходил).

## Итог сессии (2026-10-25)

**Признали проблемой (процесс, не код):**
- Визуальный UI не проектировался: ни одного макета в репо, спека отложила
  «exact mockup reproduction», эстетику оценивал только модельный контур (п. 3).
- Планирование только наращивало сложность: планы без упрощений, слоп входил в момент
  утверждения плана (п. 2).
- Поверхность конфигурации выросла (99 env-плейсхолдеров, 20 пилотных переменных) при
  гейте «Simple first use» — риск без вердикта до живого прохождения настройки (п. 4).
- Фрикшн: `start-pilot.sh` не валидирует Jira-креды — поздний малопонятный 401 (п. 1).

**Отклонили (претензии к решениям — решения были утверждёнными):**
- Требование Jira-кредов — внешнее ограничение Atlassian agile API, спринт обязателен
  по плану (п. 1).
- Пункт меню Tasks, чекбоксы, Run selected, автодискавери-поллер — дословно из
  утверждённой спеки (п. 3).
- «Самовольные слои» — структура пилота одобрена планом, запреты на спекулятивную
  общность соблюдены (п. 2).

**Принятые решения:**
- Правило «макет до плана» для UI-фич: статический макет в репо, просмотр оператором
  до утверждения плана.
- Качество закладывается на стадии планирования: минимальная версия, расширение
  существующего, явное оправдание каждого нового слоя; adversarial-проход
  саб-агентом-критиком.
- Постулаты проекта + правила планирования внесены в AGENTS.md (правка исполнена
  2026-10-25, не закоммичена).

**Уходит в отдельные задачи (по явному заданию оператора):**
1. **UX/UI-сессия (следующая):** входная точка, клик-флоу, макеты, возможный
   редизайн `/tasks`; ограничения и входные материалы — п. 3.1. Промпт сессии
   выдан оператору.
2. Fail-fast проверка Jira-кредов в старт-скрипте (из п. 1).
3. Динамическая конфигурация — кандидат в майлстоун после UX-сессии и прохождения
   оператором пути настройки (п. 4).

**Незакрытые вопросы из пунктов:** оба из п. 1 (принятие кредов как цены discovery
закрыто решением «остаётся как есть» в ходе обсуждения; fail-fast — задача 2).
